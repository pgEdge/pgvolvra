# Decisions

Every entry here has been argued once already. If you want to reopen one, the
bar is a reason that is not in this file — not a preference.

Each decision records what was chosen, what it beat, and **why the runner-up
lost**, because that last part is what saves the argument next time.

---

## pgVolvra is not a PostgreSQL extension

*How it installs.*

The core is **plain SQL** — schema, functions and triggers — installed with
`psql -f sql/volvra.sql`. That is the supported path everywhere, and the single
most important constraint in the project.

`CREATE EXTENSION` needs the script to be on the **database server's
filesystem**, which is exactly what managed providers do not give you. RDS,
Aurora, Cloud SQL, Supabase and Neon are the market this product exists for, so
requiring an extension would forfeit it. A C extension would forfeit it twice
over, by also requiring a compiled `.so` and a superuser.

`extension/` therefore packages the *same generated SQL* as an optional
convenience for self-hosted users who prefer `CREATE EXTENSION`. It is
generated by `extension/build.sh`, never hand-maintained, so the two cannot
drift. Nothing in the engine depends on it, and nothing in the test matrix
requires it.

**If a proposal starts "since we're an extension anyway…", the premise is
wrong.**

The packaging is pure SQL — two text files, nothing compiled — so one
generated script serves PostgreSQL 14 through 19 and one checksum covers them
all. A distribution package is still built per major version, because each
major version has its own share directory, but every package carries identical
SQL. The multiplication is in packaging metadata, not in the build.

Three costs come with the extension method, and each is a reason the plain SQL
path is the supported one:

1. It needs the files on the **database server's** filesystem, so it needs root
   on that host. That rules out every managed provider, which is the whole
   reason this decision exists.
2. The choice is made once per database and cannot be reversed. PostgreSQL
   removed `CREATE EXTENSION ... FROM unpackaged` in 13, so a plain install can
   never be adopted into an extension, and the reverse means `DROP EXTENSION`,
   which drops the history with it.
3. It updates only through `ALTER EXTENSION UPDATE`, which needs an upgrade
   script named for the version being left behind. Re-running the plain script
   against an extension install leaves the recorded version stale, and a later
   dump and restore loses the changes.

## The repository stays pgEdge-attributed

*Where this lives, and who owns it.*

**Decided 2026-09-08.** Every reference stays `pgEdge`: the copyright
in `LICENSE.md` and `docs/LICENSE.md`, the `repo_url` and copyright in
`mkdocs.yml`, the CI badge and issue links in `README.md` and the docs,
and the Go module paths under `github.com/pgedge/`.

The repository was developed in a personal account and moved to the
pgEdge organisation on 2026-09-15. Keeping every reference pointing at
`pgEdge` throughout meant the move changed nothing but the remote: no
rewritten links, no churned Go module path.

**Amended 2026-09-14.** The repository is named `pgvolvra`, all
lowercase, and the Go module paths follow it:
`github.com/pgedge/pgvolvra/cli` and `.../companion`. The product is
still written **pgVolvra** everywhere a person reads it.

Lowercase for two reasons. Go module paths are case-sensitive, and the
module proxy escapes every capital as `!` plus the lowercase letter, so
`pgVolvra` would appear as `pg!volvra` in proxy URLs and in every
user's module cache. And it is what the ecosystem does: pgBouncer ships
from `pgbouncer/pgbouncer`, pgBackRest from `pgbackrest/pgbackrest`.
The capitalised name is the product; the repository is lowercase.

Changed while it was still free - no tags, and the module had never
been published, so no import path existed anywhere.

The known cost until the transfer: the CI badge does not render and the
issue links resolve to the wrong place. That is accepted deliberately.
Do not "fix" these references.

## The product version is not the schema version

*What the version number means.*

Two counters, deliberately separate:

- **`volvra.schema_version`** is an internal migration counter (currently 5).
  It exists so the installer knows which migrations to run, and it increments
  whenever the on-disk shape changes.
- **The product version** (`extension/volvra.control`) is a release decision.
  It is **1.0.0-beta1**, the first release.

Coupling them was tried and was wrong: it made an internal implementation
detail set the number users would see, so five refactors would have looked like
five releases.

Known gap while unreleased: the extension packaging ships only a base install
script, so an extension-installed database has **no `ALTER EXTENSION UPDATE`
path**. Once there is a released version to upgrade *from*, `build.sh` must also
emit `volvra--<old>--<new>.sql`. Because the installer is a version-aware
migration runner, that file can be byte-identical to the install script — but it
has to exist, or the only upgrade is a drop and recreate, which destroys the
history.

## `covered` / `uncovered` / `coverage`

*Whether volvra is recording a table's changes, so a mistake on it can be
undone.* Schema v5, 2026-09-07.

**Beat:** `armed` / `unarmed` (the original), `protected`, `tracked`,
`recoverable`, `watched`.

- **`armed` was the original and lost on two counts.** It is jargon — a user
  asked what it meant, which is the only evidence that matters — and it borrows
  a weapons connotation from alarm systems that a data-recovery tool does not
  want. It also has no usable noun: "armedness" is not a word, and the product
  needs one.
- **`protected` was the strongest runner-up** and reads best to a non-technical
  buyer. It lost because it **overclaims**: it implies prevention, and volvra
  prevents nothing. The bad `UPDATE` still runs. Promising protection and
  delivering recoverability is the kind of gap that surfaces during an incident.
- **`tracked`** (the git vocabulary) is instantly familiar to developers and
  accurate, but it describes the *mechanism* rather than the *benefit*. It is
  the right word for a diff tool and the wrong one for insurance.
- **`recoverable`** is the most descriptive of the benefit but also overclaims:
  a `TRUNCATE` in `allow` mode is recorded and *not* recoverable, so the word
  would be wrong in a case that actually matters.
- **`covered` won** because the insurance framing is exactly right — coverage
  does not prevent the accident, it makes it recoverable, and nobody expects
  otherwise from the word. It gives a real noun (*"undo coverage"*, *"a coverage
  gap"*), its negative is plain English, and it fits a column header.

Consequence: `status().covered`, `status().truncate_covered`,
`volvra.uncovered(schema)`, CLI `cover` / `uncover` / `uncovered`.

**`enable` / `disable` deliberately kept their names.** They are the verbs the
original handoff specified, they are already plain, and they are the SQL API
that anything else would have to migrate.

## `skip_conflicts`, not `force`

*What `undo` does with a row that has changed since it was captured.*

**Beat:** `force`, `overwrite`, `ignore_conflicts`.

`force` was implemented first and the test suite caught it destroying the very
change it was supposed to protect — it had been written to drop the guard rather
than to skip the row. The name was the cause: `force` invites "do it anyway",
and "anyway" is the data loss the conflict guard exists to prevent.

`skip_conflicts` says what actually happens. The two outcomes are **refuse** and
**skip**; there is deliberately no third option that guesses. If someone asks
for `--force`, the answer is that it does not exist on purpose.

## `actor` and `db_user`, two columns

*Who made the change.*

One column was tried and could not be honest. `actor` is app-declared
(`SET LOCAL volvra.actor = 'svc:pricing'`) and is **spoofable by design** —
that is what makes it useful, because only the application knows which of its
own services acted. `db_user` is the authenticated principal and is the audit
column.

Collapsing them would mean either losing application context or presenting a
spoofable value as an audit record. Two columns, named for what they are.

## `seal` / `verify`, not `sign` / `audit`

*Making the history provable.*

**`sign`** was rejected because it implies a cryptographic signature with a
private key, and this is a hash chain — no key, no non-repudiation against the
database owner. Calling it signing would promise a property it does not have.

**`audit`** was rejected because the product already has an audit trail
(`undo_log`) and `verify` is not it. `seal` and `verify` say what happens: a
span is closed, and the closure can be re-checked.

---

## `forget`, not `delete` or `redact`

*Erasing one subject's history.*

`delete` was too weak a word for something irreversible that spans many rows,
and it collides with the SQL statement. `redact` is what the default mode
*does*, but the function also has a `hard => true` mode that deletes outright,
so naming it after one mode would mislead in the other.

`forget` matches how the request arrives — "forget me" — and the mode says
which mechanism carried it out.

---

## `maintain`, one verb

*The scheduled job.*

Three functions (`ensure_partitions`, `purge`, `seal`) were three chances to
forget one, and the one people forget is `seal`, which is the one that silently
widens the window where tampering is undetectable. A single verb removes the
choice. The parts remain callable individually for anyone who wants them.

## The product name is pgVolvra; the schema is `volvra`

*What the thing is called, and what you type.*

**Decided 2026-09-07, prefixed 2026-09-12.** The brand is **pgVolvra**.
Every identifier stays `volvra`: the schema, `volvra.undo()`,
`volvra.replay()`, the three roles, the CLI binary, the Go module paths
and `sql/volvra.sql`.

`Torna` ("it returns", Italian) was the alternative and the better real
word. Volvra won on being ownable: an invented word is clearable and
searchable in a way a common Italian verb form is not, and the whole
point of picking a name early is to stop renaming things.

The `pg` prefix was added later, and deliberately does not reach the
API. `pg` marks membership of the PostgreSQL ecosystem rather than
extension-hood -- pgBouncer, pgAdmin and pgBackRest are none of them
extensions -- so it does not contradict this product not being one.
**pgvector is the precedent**: the project is `pgvector`, the type and
functions are `vector`, and nobody is confused. Users type the API
name; the brand is what they search for and cite.

An org-prefixed form such as `pgedge-volvra` was considered and
rejected. pgEdge's own naming splits two ways: standalone components
carry bare names (Spock, LOLOR, ACE, Snowflake), while the pgEdge
prefix goes on category products (pgEdge Vectorizer, pgEdge
Anonymizer). More decisively, this product's whole claim is that it
runs on RDS, Aurora, Cloud SQL, Supabase and Neon, and an org-prefixed
name tells a Supabase or Neon user it is somebody else's platform
tooling. That is the audience the design constraints exist to reach.

Capitalisation is **pgVolvra**, matching pgBouncer and pgAdmin rather
than lowercase pgvector.

Trademark and registry clearance is still outstanding: domains, USPTO
classes 9 and 42, and GitHub, npm and PyPI. A search on 2026-09-11
found no software collision for either form, but `volvra.in` is an
active consumer-products brand in a different class. The prefixed form
is the better one to file, being a more distinctive composite mark.
Clearance may still force a change before any public release, and
until it completes every public use of the name carries that risk.

Reopening this needs a clearance result, not a preference.

## The licence is the PostgreSQL License

*How the software is licensed.*

**Decided 2026-09-07.** pgVolvra is licensed under the PostgreSQL
License, matching Spock and the rest of the pgEdge portfolio.

The licence text is in `LICENSE.md` at the repository root and in
`docs/LICENSE.md`, because MkDocs cannot alias a file from outside the
docs directory. Both copies must stay identical.

The choice was between the PostgreSQL License and holding the code
closed. A liberal open source licence was chosen because pgVolvra's
value is in being installable anywhere, including on managed providers
where nothing can be compiled, and a restrictive licence would work
against exactly the reach the design buys.
